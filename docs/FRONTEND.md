# フロントエンド設計

## 1. 目的と対象

amazon-explorer の実検索用UIは Streamlit で実装されている。利用者の自然文入力を受け取り、バックエンドの検索パイプラインを同期実行し、採点済みの商品候補を順位順に表示する。次期デスクトップUIは [frontend/](../frontend/) のReact + StyleX製オフラインモックとして実装し、実検索用UIとバックエンドの接続は維持する。

この文書は現行の `app.py` と `src/ui/streamlit_ui.py` を正として、画面構成、状態管理、バックエンドとの境界、拡張時の規約を定義する。画面上の文言と操作仕様は [統合済みUI設計](#統合済みui設計)、検索処理の内部構成は [BACKEND.md](BACKEND.md)、承認済みの次期検索体験は [SEARCH-FLOW.md](../SEARCH-FLOW.md)を参照する。

### 1.1 次期フロントエンドの自前開発方針

2026-09-11の利用者の明示決定により、次期フロントエンドはこのリポジトリで自前開発する。外部納品を待つ制約は解除する。この文書の[視覚統一契約](#13-次期uiの視覚統一契約)と[オフラインモック](#14-オフラインモック)、[SEARCH-FLOW.md](../SEARCH-FLOW.md)を、自前で作成する画面の目標仕様と受入条件とする。

文書の正本化に続く利用者の実装指示を [EXEC-117](GOAL.md#exec-117-react-stylexのオフライン画面) で実施し、任意入力から結果・履歴まで操作できるモックを追加した。以下のStreamlitの説明は既存の実検索用UIの記録であり、次期画面の実装済み仕様を示さない。モックのChromiumでのオフライン受入確認済みで、実バックエンド/API接続は後続作業とする。

実装はReact 19 + TypeScript + Vite 8 + StyleXとし、[配置と実行手順](#141-配置と実行手順)を正本とする。通常の実行・遷移ボタンの外枠は176×48px、検索履歴一覧の `削除`・`開く` は96×36pxとする。ON/OFFを切り替えるトグルスイッチは別寸法とする。現行Streamlitを自動で置き換えず、次のローカルバックエンド接続では表示・承認契約を合わせる。検索実行はローカル専用・単一host・単一process・worker 1本を維持する。実サービス検証は送信先・内容・回数・credential・費用の事前提示と明示承認を必要とする。

## 2. エントリーポイント

```text
uv run streamlit run app.py
  -> app.py
  -> src.ui.streamlit_ui.main()
```

`app.py` は `main()` の呼出しだけを担う。ページ設定、ウィジェット、状態管理、表示処理は `src/ui/streamlit_ui.py` に置く。検索、外部API通信、正規化、採点をUIへ実装しない。

## 3. 画面構成

ページは `layout="wide"` を使い、次の領域で構成する。

```text
ページ
├── サイドバー
│   ├── Bonsai接続先
│   ├── Amazonドメイン・言語・取得件数
│   ├── Outscraper APIキー設定状態
│   ├── Bonsai稼働状態
│   ├── 表示件数スライダー
│   └── スコア重み（SHOW_DEBUG_INFO=true の場合だけ）
└── メイン領域
    ├── タイトル
    ├── 自然文入力フォーム
    ├── 実行中スピナーまたはメッセージ
    └── 商品結果カード
```

主な表示関数:

| 関数 | 責務 |
|---|---|
| `main()` | ページ全体、状態初期化、フォーム送信、検索呼出し |
| `render_status_panel()` | 接続先と設定状態をサイドバーへ表示 |
| `render_results()` | 件数表示と上位商品の反復表示 |
| `render_product()` | 画像、スコア、価格、評価、条件、商品リンクを1件分表示 |
| `render_terms()` | 条件語の一覧を区切り文字付きで表示 |
| `format_price()` | 円価格または「価格不明」へ整形 |
| `format_rating()` | 評価とレビュー件数を表示用文字列へ整形 |

## 4. 状態管理

永続的なフロントエンド状態には `st.session_state` を使う。

| キー | 型 | 初期値 | 用途 |
|---|---|---|---|
| `scored_products` | `list[ProductScore]` | `[]` | 最後に成功した検索結果を再実行間で保持する |
| `cache_scope` | `str` | `secrets.token_hex(16)` | バックエンドのキャッシュキーをセッションごとに分離する |

`cache_scope` は同一セッション中は維持され、別のStreamlitセッションでは異なる。これはキャッシュキーの衝突を避けるための値であり、ユーザーID、認証情報、秘密情報ではない。キャッシュファイルの保存ルート自体は共通である。

Bonsaiの疎通確認は `@st.cache_data(ttl=5, show_spinner=False)` を付けた `bonsai_is_available()` で5秒間だけ再利用する。商品検索結果そのものにStreamlitの共有キャッシュは使わない。

### 4.1 再実行時の挙動

Streamlitはウィジェット操作ごとにスクリプトを再実行する。表示件数を変更しても `scored_products` は残るため、外部APIを再実行せず表示件数だけを変えられる。検索失敗時は新しい結果を代入しないため、すでに成功結果があればその結果が画面下部に残る。

## 5. イベントとデータフロー

```text
利用者が検索フォームを送信
  -> 前後空白を除いた入力が空か確認
  -> スピナーを表示
  -> run_product_search(user_input, cache_scope=session_scope)
  -> list[ProductScore] を session_state へ保存
  -> 表示上限まで結果カードを描画
```

フォーム未送信時は外部処理を行わない。空白だけの入力では警告を表示し、バックエンドを呼ばない。

現行処理は同期実行である。Bonsai呼出し、Outscraperタスク作成とポーリング、正規化、採点が終わるまで同じStreamlit実行が待機する。ジョブID表示、段階別の進捗率、キャンセル、バックグラウンド継続は実装されていない。

## 6. バックエンド境界

UIが直接呼ぶ公開境界は次である。

```python
run_product_search(
    user_input: str,
    *,
    use_cache: bool = True,
    cache_scope: str = "local-cli",
) -> list[ProductScore]
```

Streamlitは `use_cache` を指定しないため、`ENABLE_CACHE` が真ならキャッシュを読む。返却値は総合スコア降順の `ProductScore` リストであり、UIは外部APIの生レスポンスや正規化前データへ依存しない。

UIは設定状態の表示にグローバルな `settings`、Bonsaiの疎通確認に `is_bonsai_running()` を参照する。それ以外のBonsai・Outscraperクライアント、キャッシュリポジトリ、採点サービスを直接呼ばない。

## 7. エラー境界

検索中に発生した例外はUI層で型を問わず捕捉する。

- サーバーログ: `LOGGER.exception("Product search failed")` でスタックトレースを記録する
- 利用者画面: 「検索に失敗しました。設定と外部サービスの状態を確認してください。」という固定文言を表示する

画面へAPIキー、外部レスポンス本文、内部パス、スタックトレースを直接表示しない。運用者が原因を調べる手順は [統合済みトラブルシューティング](DEVELOPMENT.md#統合済みトラブルシューティング)、秘密情報の扱いは [SECURITY.md](SECURITY.md)を参照する。

## 8. 設定境界

UIが参照する設定は次のとおりである。

| 設定 | 現行の用途 |
|---|---|
| `BONSAI_BASE_URL` | 接続先表示と疎通確認 |
| `OUTSCRAPER_API_KEY` | 値そのものではなく、設定済みかどうかだけを表示 |
| `OUTSCRAPER_DOMAIN` | 対象Amazonドメインの表示 |
| `OUTSCRAPER_LANGUAGE` | 言語の表示 |
| `OUTSCRAPER_LIMIT` | 外部APIの取得上限表示 |
| `SEARCH_RESULT_DISPLAY_LIMIT` | 表示件数スライダーの初期値 |
| `SHOW_DEBUG_INFO` | サイドバーへ重みを表示するか |

表示件数は画面上で1件から30件まで選択できる。初期値は `min(SEARCH_RESULT_DISPLAY_LIMIT, 30)` である。Outscraperの取得件数とは別の設定であり、表示件数を減らしても外部APIの取得上限は減らない。

## 9. セキュリティとプライバシー

- APIキーの値は表示しない。「existing」または「missing」だけを表示する
- 検索条件はBonsaiとOutscraperへ送られ、抽出属性と商品結果はローカルの `cache/` に保存され得る
- セッションscopeは画面に表示せず、認証トークンとして使わない
- 商品画像と商品リンクは外部由来のURLである。現行モデルはこれらのURLスキームやホストを厳密に制限していない
- Streamlitの利用者認証、認可、レート制限、利用者別の永続保存領域は未実装である

外部公開する前に必要な対策は [SECURITY.md](SECURITY.md) と [統合済み制約](REQUIREMENTS.md#統合済み制約) を参照する。

## 10. 現在の制約

- 長時間のOutscraper待機中も画面要求を占有する
- 進捗表示は単一のスピナーだけで、現在段階や残り時間を画面へ出さない
- 検索のキャンセル、履歴、比較、お気に入り、ページネーションはない
- 接続状態はBonsaiだけをHTTP確認し、OutscraperはAPIキーの有無だけを確認する
- スコア重みは表示できるが、画面から変更できない
- レスポンシブ表示はStreamlitの標準挙動に依存する
- UI専用の自動テスト、キーボード操作試験、スクリーンリーダー試験は未整備である

これらは現行機能として扱わず、実装する場合は [技術的負債トラッカー](ISSUES.md#統合済み技術的負債トラッカー) と [大規模タスク一覧](GOAL.md#統合済み大規模タスク一覧) で優先順位を管理する。

## 13. 次期フロントエンド契約

次期UIはReact + StyleXで実装し、[SEARCH-FLOW.md](../SEARCH-FLOW.md) のStep、確認内容、利用者向け状態を描画する。対応するserver-side状態は [BACKEND.md](BACKEND.md#13-次期検索バックエンド-v2基盤を一部実装) を正とする。

画面とオフライン状態遷移は実装済みで、以下のserver応答・実画像生成・実検索・永続履歴は接続時の目標契約である。モックが実装した範囲と簡略化は [14節](#14-オフラインモック) に示す。

次期画面を人が操作する順序、各ボタンの結果、API利用前の確認は、リポジトリ直下の [SEARCH-FLOW.md「UI操作フロー」](../SEARCH-FLOW.md#ui操作フロー) を正とする。

1. 自然文入力と `条件を整理`
2. `必ずほしい`、`できればほしい`、`避けたい`、入力価格またはAIが提案した目安の確認と編集
3. 既定OFFの参考画像トグル
4. ON時は参考画像1枚を生成して確認待ちにする。`了承して生成` の後だけ条件別偽画像を生成し、全体を確認して最終確認へ進む
5. 検索先、比較候補の上限（最大48件）、比較項目、画像、この承認で商品検索を1回実行することを示す最終確認
6. `商品を探す`、`商品情報を整理`、`商品の特徴を確認`、`希望条件と比較`、`結果を準備` の5段階待機
7. 5段階が完了した取得・評価画面と `結果を見る`
8. 条件との近さ、条件ごとの `一致`・`未確認`・`不一致`、商品情報による確認と参考画像による外観補助の区別、避けたい条件への該当を示す結果
9. 完了した検索の履歴一覧と、保存済み結果の再表示

初回実装の共通ヘッダー右側には、検索中の画面から履歴一覧へ遷移する `検索履歴` だけを置く。設定ボタン、設定画面、設定用routeは今回作らず、将来の設定仕様が確定した変更で追加する。

結果は固定3件へ切り捨てず、初期10件を表示する。表示件数は現行Streamlitと同じ1〜30件で変更でき、変更しても検索や評価は再実行しない。

通常画面は、session／run／request等の内部ID、外部サービス名、model名、attempt、digest、hash、証拠値、API call数、token数、JSON、TF-IDF、CLIP、pHash、Hamming距離、ranking profile、raw score、内部component、実weight、採用言語、外部APIの単価・見積額・合計額・金額上限を描画しない。検索語は通常閉じた `検索語を確認・修正` に置く。

外部処理の実行可否はサーバー応答を正とする。先行1枚の作成を1回、1計画を最大2回と数え、既定では初回生成前 `参考画像を使う（残り2回）`、初回生成後 `作り直せる回数：残り1回`、作り直し実行後 `残り0回` とする。この値を後続画像の枚数やAPI call数として描画しない。先行画像の了承後に行う偽画像の生成は、同じ了承に対して1回だけである。最終確認では現在のsingle-use承認で商品検索を1回実行することを示し、検索クォータの残数として描画しない。残り回数をbrowserで推測または先行減算せず、予約後の応答で更新する。`残り0回` なら先行画像の作り直しを無効にする。

先行1枚の予約に失敗して外部要求を0件のまま止めた場合は残数を維持する。先行要求を開始した後は、失敗しても1回を使用済みとして扱う。フロントエンドはこの判定を再実装せず、サーバーが返す残数だけを表示する。後続生成が失敗した場合は部分採用や自動再試行をせず、残数内で先行1枚の作り直しと再確認へ戻るか、画像なしで続行する。

Step 2の画面状態は `参考画像を1枚生成しています`、`このイメージでよいですか？`、`比較用の偽画像を生成しています`、`画像の準備ができました` を分ける。先行1枚の成功通知、画面再読込、拡大表示を了承へ変換せず、明示ボタンだけが後続生成を開始する。了承済みの参考画像1枚と、選択した視覚条件1〜3件に対応する偽画像を別枠にし、偽画像ごとに変更した条件を示す。各画像へ `AI生成イメージ` を付ける。参考画像・比較画像は画像自体を拡大操作にし、独立した「拡大」ボタンを置かない。ホバー時は画像中央に白い虫眼鏡アイコンを黒い円形背景で表示し、カーソルをzoom-inにする。クリックまたはタップでライトボックスを開く。キーボードのフォーカス時もアイコンを表示し、Enter・Spaceで開ける。閉じた後は元の画像へフォーカスを戻す。全画像を確認した後の主要操作は `最終確認へ` とする。

先行1枚の確認が15分で期限切れになった場合、了承を無効にし、残数内の作り直しまたは画像なし続行へ案内する。期限切れと実行済みの判定はserverを正とし、browserの時計だけで実行を許可しない。

内部状態や技術メタデータはtyped APIから通常画面用の表示モデルへ明示変換する。未知fieldをそのまま一覧化する汎用JSON viewer、内部タグの自動描画、例外文字列の直接表示を実装しない。運用者向け診断情報は通常画面と認可境界を分ける。

将来の型付き条件APIも、browserへattribute key、evaluator、証拠source ID、digest、raw score、内部confidenceを渡して描画判断を委ねない。serverは条件の表示名、`matched`・`unknown`・`mismatched` に対応する利用者向け状態、短い理由、`商品情報で確認` または `参考画像による外観補助` の区分だけをallowlist済み表示modelへ変換する。内部の `conflict` は矛盾がある旨を添えた `unknown` 表示へ変換する。フロントエンドは `unknown` を不一致や一致へ変えず、必須状態によるserverの順位を並べ替えない。この契約は自前開発する次期画面の目標仕様であり、実装・API接続と検証は後続作業で行う。

実サービスの画像生成、検索、承認digest、費用reservationをbrowserへ実装しない。React + StyleXの次期UIはtyped APIと状態遷移を使う。オフラインモックは同じ画面部品へ合成応答を渡し、実バックエンドを使わず操作を再現する。現行 `st.session_state` の2キーだけではこの契約を満たさない。

待機中は確定していない進捗率や残り時間を作らず、実数が確定してから商品件数を表示する。状態変化は色だけに頼らず文字とアイコンを併用し、`aria-live="polite"` で通知する。処理完了後は自動遷移せず、`結果を見る` を有効化する。取消はserverが安全な取消を保証する状態だけに表示する。

待機画面は進行状況と `WaitingConditionsSummary` の2カラムにする。`WaitingConditionsSummary` は右側へ常時表示するページ内コンポーネントであり、承認済みの条件、価格、検索先、比較候補の上限、参考画像利用の有無だけを読み取り専用で描画する。郵便番号、お届け先、検索語、内部情報を表示モデルへ含めず、Dialog、Sheet、開閉ボタン、overlay状態を持たせない。

不足属性の提案も第一確認の条件一覧へ含める。利用者には属性の名前・意味・値・必須/希望/除外を示し、内部のregistry keyやevaluatorの承認を別操作として要求しない。関係が曖昧な提案は確認事項とする。EXEC-083のbackend契約に対応する目標仕様であり、次期画面の実装・接続は未確認である。

### 13.1 モーダル系コンポーネント境界

次期UIは、短い確認または補助参照だけを共通コンポーネントへ切り離す。

| コンポーネント | 用途 |
|---|---|
| `ImageLightbox` | 参考画像・偽画像・結果の商品画像の拡大と閉じる。参考画像・偽画像が複数ある場合だけ前後移動 |
| `RegenerateImagesAlertDialog` | 先行1枚の作り直しと後続画像の失効、現在と実行後の残り回数の確認 |
| `CancelSearchAlertDialog` | serverが安全に取消可能と返した場合だけ検索中止を確認 |
| `StartNewSearchAlertDialog` | 現在結果を履歴から復元できない場合だけ離脱を確認 |
| `RetryExecutionAlertDialog` | 外部処理を再実行する場合だけ、対象範囲とサーバーが返せる場合の残り回数、または再試行可否を確認 |
| `DeleteHistoryAlertDialog` | 履歴1件の復元不能な削除を確認 |

検索語編集、待機中の読み取り専用条件要約、商品カードの検索条件はページ内要素を維持する。条件入力、最終確認、待機、結果、履歴一覧をDialog内へ実装しない。Select、Popover、入力エラー、工程エラーもDialogへ置き換えない。

モーダル系コンポーネントは同時に1つだけ開き、nested Dialogを禁止する。開く前の要素を保持して閉じた後にフォーカスを戻す。背景をinertにし、フォーカストラップ、見出しと説明の関連付け、body scroll lockを実装する。`Esc`、背景クリック、キャンセルは実行操作へ変換しない。破棄・取消・外部処理の実行ボタンを初期フォーカスにしない。

### 13.2 検索履歴の表示状態

履歴は完了済み検索の表示用スナップショットをtyped APIで扱い、処理キャッシュを一覧として直接公開しない。

```text
HistoryListState = idle | loading | ready | empty | failed
HistoryDeleteState = idle | confirming | deleting | failed
HistoryDetailState = loading | ready | not_found | failed
```

一覧用モデルは検索日時、保存期限、自然文の短い要約、価格条件、参考画像利用の有無、比較件数だけを持つ。詳細用モデルは確定条件と順位付け済みの商品表示モデルを持つ。内部IDをrouting pathやDOMへ露出せず、serverが発行する推測困難な公開用locatorを使用する。表示モデルへ郵便番号、お届け先、query parameter、provider、model、token、digest、raw score、内部componentを含めない。

正常に `completed` へ到達した検索は、0件も含めて1履歴項目を冪等に保存する。同じ完了通知や画面再読込で重複項目を作らない。履歴保存に失敗しても現在の結果カードを消さず、再保存操作を提供する。保存済み結果から `新しく検索` を始める場合は確認せず、保存できておらず離脱後に復元不能な場合だけ確認する。

履歴一覧、履歴詳細、履歴削除の要求は、画像生成、商品取得、商品属性整理、採点を呼べないread/delete専用application serviceへ接続する。`再読込` と削除再試行も同じ境界を守る。履歴詳細の表示件数とaccordion状態は画面状態であり、保存済み順位と結果データを更新しない。

履歴1件を削除するときは対象カードだけをpending表示にし、成功レスポンス後に一覧から外す。失敗時はカードを残す。完了日時から30日の期限へ到達した項目はserverが物理削除し、一覧へ返さない。個別削除後または期限切れ後に同じlocatorを開いた場合はnot foundの理由を平易に示して履歴一覧へ戻し、外部検索で再構築しない。


## 統合済みUI設計

> 統合元: `docs/UI.md`。統合前の文書は `docs/old/` に保存する。


> **標準文書との関係:** フロントエンド構造と実装境界は [FRONTEND.md](FRONTEND.md) を正本とする。この文書は画面表示、操作、状態、視覚仕様を詳細化する。

### 1. 目的

この文書は、amazon-explorer のStreamlit画面で利用者が見る要素、操作手順、表示規則、エラー表現、アクセシビリティ上の現状を定義する。実装構造と状態管理は [FRONTEND.md](FRONTEND.md)、承認済みの次期画面フローは [SEARCH-FLOW.md](../SEARCH-FLOW.md)を参照する。

### 2. 想定利用者と利用目的

利用者は、商品名だけでなく「静か」「白い」「1万円以内」「避けたい条件」のような要望を日本語の自然文で入力し、条件への近さを比較する。表示順位は推薦や購入保証ではなく、取得できた候補を現行スコア式で並べた参考情報である。

現行UIはローカル利用を主対象とする。ログイン、複数利用者向けの履歴管理、購入処理は提供しない。

### 3. 画面仕様

#### 3.1 ページ設定

| 項目 | 現行値 |
|---|---|
| ブラウザページタイトル | `Amazon Product Search` |
| レイアウト | `wide` |
| 画面タイトル | `Amazon類似度検索` |

#### 3.2 サイドバー

「設定」見出しの下に次を表示する。

| 表示 | 内容 |
|---|---|
| `Bonsai: ...` | `BONSAI_BASE_URL` の値 |
| `Amazon: ... / ...` | Outscraperのドメインと言語 |
| `取得件数: ...` | Outscraperへ要求する最大件数 |
| `Outscraper API key: existing/missing` | APIキーが空でないかだけを成功・警告表示 |
| `Bonsai Server: running/not running` | `/models` の疎通結果を成功・警告表示 |
| `表示件数` | 1から30のスライダー |

`SHOW_DEBUG_INFO=true` の場合だけ、商品名・属性・価格の総合係数と、必須語・色語・特徴語・優先語・関連語の重みをJSON表示する。採点に使う8つの重みは確認できるが、全設定の診断画面ではない。

ここで挙げた接続先、APIキー設定状態、サーバー稼働状態、debug JSONは現行Streamlitの診断表示であり、次期の通常UIへ継承しない。次期UIでは、利用者が対処できる問題が起きた場合だけ平易な案内を表示し、診断情報は運用者向けログへ分離する。

#### 3.3 検索フォーム

- ラベル: `商品を検索`
- 入力形式: 高さ120pxの複数行テキスト
- 実行ボタン: `検索`
- 空白だけの入力: `検索条件を入力してください。` と警告し、検索しない

入力例:

```text
1万円以内で、白くて静かな日本語配列のワイヤレスキーボード。
テンキー付きは避けたい。
```

条件を具体化するときは、商品種別、価格帯、色、必要な特徴、避けたい特徴を一つの文章に含める。

### 4. 検索中と検索後の状態

#### 4.1 検索中

検索開始後は次のスピナーを表示する。

```text
商品候補を取得してスコアリングしています。
```

検索は同期処理である。スピナーは段階別進捗、Outscraperのポーリング回数、完了予定時刻を表示しない。処理中にブラウザを閉じた場合の継続やキャンセルも保証しない。

#### 4.2 0件

検索が正常終了しても表示対象がなければ、次を情報表示する。

```text
表示できる検索結果がありません。
```

0件はエラーとは限らない。Outscraperが正常に0件を返した場合や、正規化でタイトルなし・未対応通貨の商品が除外された場合にも発生する。

#### 4.3 結果あり

区切り線の後に次の件数表示を行う。

```text
{取得結果数}件中 {実際の表示数}件を表示
```

`表示件数` は画面に描画する上限であり、検索済みの結果リストやOutscraperの取得件数を変更しない。スライダーを変更しただけでは再検索しない。

### 5. 商品カード

商品1件を枠付きコンテナに表示し、画像列と詳細列を1対3の比率で並べる。

| 要素 | 表示規則 |
|---|---|
| 順位・商品名 | `{順位}. {title}` を小見出しとして表示 |
| 商品画像 | `image_url` があれば列幅に合わせて表示。なければ「画像なし」 |
| 総合 | `total_score` を小数3桁で表示 |
| 商品名 | `title_similarity` を小数3桁で表示 |
| 属性 | `attribute_similarity` を小数3桁で表示 |
| 価格 | `price_score` を小数3桁で表示 |
| 進捗バー | `total_score` を0から1のバーで補助表示 |
| 実価格 | 整数を桁区切りした `{価格}円`。値がなければ「価格不明」 |
| 評価 | 小数1桁。件数があれば `{評価} / {件数}件`、なければ評価だけ。評価がなければ「評価なし」 |
| 商品リンク | `product_url` がある場合だけ「Amazonで開く」ボタン |
| 条件語 | 一致、不足、避けたい条件への一致を、それぞれ値がある場合だけ表示 |

条件語は ` / ` で連結する。「避けたい条件に一致」が表示された商品は、否定条件ペナルティを受けていても候補から自動除外されたとは限らない。

### 6. スコアの読み方

総合スコアは次の要素を組み合わせ、0から1へ制限した値である。

```text
0.45 × 商品名類似度
+ 0.35 × 属性類似度
+ 0.20 × 価格スコア
- 否定条件ペナルティ
```

- `商品名`: 入力条件と商品名のテキスト類似度
- `属性`: 商品説明等との類似度または重み付き条件一致率
- `価格`: 指定または推定価格帯への近さ
- `一致した条件`: 採点に使われた条件のうち見つかったもの
- `不足している条件`: 採点対象だが見つからなかったもの
- `避けたい条件に一致`: 商品テキスト中で見つかり、減点対象になったもの

スコアは取得データと設定に依存する。商品の品質、安全性、在庫、価格の最新性を保証しない。詳細な計算規則は [DESIGN.md](BACKEND.md#統合済み全体設計) と [BACKEND.md](BACKEND.md)を参照する。

### 7. メッセージとエラー表示

| 状況 | 種別 | 利用者向け表示 | 次の行動 |
|---|---|---|---|
| 入力が空 | warning | `検索条件を入力してください。` | 商品条件を入力して再送信 |
| APIキーなし | sidebar warning | `Outscraper API key: missing` | `.env` を設定してアプリを再起動 |
| Bonsai疎通不可 | sidebar warning | `Bonsai Server: not running` | Bonsaiサーバーと接続先を確認 |
| 検索処理の例外 | error | `検索に失敗しました。設定と外部サービスの状態を確認してください。` | 起動ターミナルのログを確認 |
| 正常な0件 | info | `表示できる検索結果がありません。` | 条件を広げて再検索 |
| 商品画像なし | info | `画像なし` | 商品名やリンクで判断 |

検索例外の詳細は画面に表示しない。APIキー、外部レスポンス、スタックトレースの漏えいを避けるためである。診断方法は [TROUBLESHOOTING.md](DEVELOPMENT.md#統合済みトラブルシューティング)を参照する。

### 8. 操作フロー

1. サイドバーで Bonsai が `running`、Outscraper API key が `existing` であることを確認する
2. 商品条件を自然文で入力する
3. 「検索」を押す
4. スピナーが消えるまで待つ
5. 総合スコアだけでなく、一致・不足・否定条件と価格を比較する
6. 必要なら表示件数を変える
7. 商品ページを確認するときだけ「Amazonで開く」を押す

商品ページの価格や在庫を最終判断の正とする。外部リンク先の内容と安全性は本アプリが保証しない。

### 9. アクセシビリティ

#### 9.1 現在利用できる手掛かり

- スコアはバーだけでなく数値とラベルでも表示する
- 状態は色だけでなく `existing/missing`、`running/not running` の文字でも示す
- 価格不明、評価なし、画像なしを文字で明示する
- 検索入力にラベル、実行操作にテキスト付きボタンを使う
- 商品リンクは用途が分かる「Amazonで開く」という文言を使う

#### 9.2 未確認・未実装

- 商品画像へ商品名に基づく明示的な代替テキストを設定していない
- フォーカス順、キーボードだけでの操作、スクリーンリーダー読み上げを試験していない
- エラー発生時のフォーカス移動やライブリージョンを独自実装していない
- 小画面、拡大表示、高コントラスト、色覚多様性の受入試験がない
- 日本語と英語が混在するステータス文言がある

公開範囲を広げる前に、Streamlitの生成HTMLを実際のブラウザと支援技術で確認する。未確認事項は [TECH-DEBT-TRACKER.md](ISSUES.md#統合済み技術的負債トラッカー) で追跡する。

### 10. UI受入確認

外部APIを呼ばない起動確認:

```sh
uv run --frozen --offline --no-sync streamlit run app.py --server.headless true
```

手動確認項目:

- ページタイトル、画面タイトル、サイドバーが表示される
- 空入力で警告が出て検索が始まらない
- 表示件数を1から30で変更できる
- APIキーの実値が画面に出ない
- Bonsai停止時も画面自体は起動し、警告表示になる
- 検索例外の詳細が画面に出ず、サーバーログには診断情報が残る
- 成功時に件数、各スコア、価格、評価、条件語、存在するリンクが表示される
- 表示件数変更だけでは検索が再実行されない

実検索を伴う確認ではOutscraperの利用料金と取得件数を事前に確認する。

### 11. 次期検索画面

現行の「検索」1操作で同期処理を始める画面は、次期検索フロー v2では次へ置き換える。次の画面構成をオフラインモックへ実装し、実データ・API接続は後続作業とする。

| 段階 | 必須表示 | 利用者操作 |
|---|---|---|
| 入力 | 自然文、2,000文字上限 | `条件を整理` |
| 条件確認 | `必ずほしい`、`できればほしい`、`避けたい`、入力価格またはAIが提案した価格の目安、参考画像トグル | `修正`、`参考画像を生成`、`画像なしで進む` |
| 参考画像・先行確認 | まず1枚、`AI生成イメージ`、了承後に生成する画像の説明、作り直せる残り回数 | `了承して生成`、`作り直す`、`画像なしで進む` |
| 参考画像・全体確認 | 了承済み参考画像1枚、比較用の偽画像1〜3枚と変更条件、`AI生成イメージ` | `最終確認へ`、`作り直す`、`画像なしで進む` |
| 最終確認 | 条件、価格、検索先、比較候補の上限（最大48件）、比較項目、画像、この承認で商品検索を1回実行すること | `修正`、`キャンセル`、`検索` |
| 待機 | `商品を探す`、`商品情報を整理`、`商品の特徴を確認`、`希望条件と比較`、`結果を準備` の5段階と、右側へ常時表示する読み取り専用の検索条件要約 | 完了を待つ、許可された場合だけ中止する |
| 取得・評価完了 | 完了した5段階、確定した商品件数、平易な注意事項 | 結果を見る、条件を見直す |
| 結果 | 条件に近い順、比較済み件数と表示件数、条件との近さ、希望に合う点、商品説明では確認できない点、避けたい条件への該当 | 1〜30件で表示件数を変更、外部商品ページを開く、新しい検索 |
| 検索履歴 | 検索日時、条件要約、価格条件、参考画像利用の有無、比較件数 | 保存済み結果を開く、1件ずつ削除、商品を探す |

共通ヘッダー右側へ追加するグローバル操作は `検索履歴` だけとし、検索中の画面から履歴一覧へ移動できるようにする。設定ボタンと設定画面は初回実装を保留し、無効な設定ボタンや空の設定画面を先行配置しない。

参考画像トグルは既定OFFとする。まず1枚だけ生成し、了承を得た後にその画像を参照して別途偽画像を生成する。作り直しは先行1枚から行い、旧了承、後続画像、最終確認を無効にする。新しい先行1枚の了承なしに後続生成へ進まない。単に最終確認画面を開いただけでは検索を始めず、`検索` の明示操作だけを商品検索の承認とする。

先行1枚は1計画で初回生成と作り直しを合わせて2回までとする。初回生成前は `参考画像を使う（残り2回）`、初回生成後は `作り直せる回数：残り1回`、作り直し実行後は `残り0回` と表示する。この回数は先行1枚の作成回数であり、後続生成の枚数やAPI call数ではない。後続生成は同じ了承に対して1回だけとし、失敗時も同じ了承を再利用しない。最終確認には `この承認で商品検索を1回実行します` と表示し、検索クォータの残数とは表現しない。本番にper-user・session・day・cost quotaはなく、画面へquota残数、外部APIの単価、見積額、合計額、金額上限を表示または入力させない。失敗時は自動再実行せず、再実行には新しい確認と承認を要求する。

正常に比較が完了した検索は、0件だった場合を含めて検索履歴へ1件として完了日時から30日間自動保存する。履歴カードには分単位の保存期限を表示する。履歴を開いたときは保存済みの条件と順位付け結果を描画するだけとし、画像生成、商品取得、商品属性整理、採点を再実行しない。履歴一覧の空、読込中、読込失敗、1件削除中、削除失敗を別の状態として表示する。履歴項目の個別削除は復元不能であることを確認ダイアログに示し、成功するまでカードを一覧から外さない。30日の期限へ到達した履歴と専有生成画像はサーバー側で物理削除し、外部処理から再構築しない。

履歴は表示用スナップショットだけを通常画面へ返す。郵便番号、お届け先、検索要求parameter、内部ID、外部サービス名、model名、token数、digest、raw score、内部評価方式は、現在結果と履歴のどちらにも表示しない。

待機画面の検索条件要約には、承認済みの条件、価格、検索先、比較候補の上限、参考画像利用の有無を表示する。右側へ常時表示するページ内サイドビューとし、開閉ボタン、overlay、Sheetは設けない。郵便番号、お届け先、検索語、内部情報は表示しない。

#### 11.1 モーダル化する範囲

次期UIでページから切り離すのは、短い確認または補助参照だけである。

| 形式 | 対象 |
|---|---|
| 画像ライトボックス | 参考画像・偽画像・結果の商品画像の拡大、参考画像・偽画像が複数ある場合の前後移動、閉じる |
| 確認ダイアログ | 先行1枚の作り直しと後続画像の失効、安全に取消可能な検索の中止、復元不能時だけの新しい検索、外部処理を行う再試行、履歴1件の削除 |

検索語編集、待機中の読み取り専用条件要約、商品カードの検索条件はページ内要素を維持する。条件入力、最終確認、待機、結果、履歴一覧をモーダルへ入れない。保存済み結果から `新しく検索` を始める場合は復元可能なので確認ダイアログを表示せず、履歴保存に失敗した場合だけ表示する。

モーダル系部品は同時に1つだけ開く。背景を操作不能にし、開いたときに安全な要素へフォーカスを移し、閉じた後は起動元へ戻す。`Esc` とキャンセルは実行操作を起こさない。ダイアログ内に別のダイアログを重ねない。

Button、Field、Toggle、Chip、Stepper、App Header、画像カード、進捗行、待機中の条件要約、結果カード、履歴カード、Overlay、Dialog、AlertDialog、Image Lightboxを共通のReactコンポーネントとして扱い、StyleXの共通定義で本契約を適用する。Figmaの変数やcomponent更新を実装の前提条件にしない。

受入確認では、本契約の色・文字サイズ・円弧の角丸と細い枠の表示・通常ボタンと履歴一覧ボタンの各寸法・操作配置・アニメーションを照合する。100%・DPR1のボタンとウィンドウでは、画素の濃度から角の線の薄れ、直線1px、円弧の幾何学的範囲外への着色がないことを検査する。状態差は文字とアイコンでも判別できることを確認する。画面起動、ブラウザ操作、mock、実サービスの検証結果は区別する。

CSSのreset層はHTMLのheadでStyleXの各層より先に登録し、開発サーバーとビルド済み画面のどちらでも共通スタイルを上書きしない順序にする。通常・無効・処理中・ホバーの各状態を実ブラウザの計算済みスタイルで確認する。

#### 13.5 ボタン

主要操作は右側へ置く。削除などの危険操作は左側へ離して配置し、危険操作であることを文言と確認内容で示す。`削除` は一覧・詳細・確認ダイアログのすべてで危険ボタンを使う。同じ寸法区分では種別によらず外枠寸法を揃え、文字を中央に置く。履歴一覧だけの小型寸法は [13.3](#133-幅高さ余白角丸) に従う。基本・危険・進む/決定/保存のすべてで、通常寸法・小型寸法とも外枠の線幅を1pxにする。

| 種別 | 通常の背景 | 通常の外枠 | 通常の文字 | ホバー時 |
|---|---|---|---|---|
| 基本 | `#000000` | `#ffffff` | `#ffffff` | 背景 `#424242`、文字・外枠は維持 |
| 危険 | `#000000` | `#901010` | `#901010` | 背景 `#424242`、文字・外枠は維持 |
| 進む・決定・保存 | `#ffffff` | `#ffffff` | `#000000` | 背景 `#000000`、文字 `#ffffff`、外枠 `#ffffff` |

危険ボタンは通常・ホバー・無効時とも文字と外枠を `#901010` に保つ。進む・決定・保存ボタンは無効時も白背景・黒文字を保つ。処理中文言と末尾の点もボタンの文字色を継承する。色の反転は操作可能なボタンのホバー時だけ適用する。

文言は意味を保って短くする。例として「削除する」は `削除` とする。確認・実行対象を長いボタン文言だけに詰めず、隣接する説明へ記載する。

| 操作 | ボタン文言 | 近くに示す内容 |
|---|---|---|
| 条件整理 | `条件を整理` | 入力内容を整理すること |
| 先行1枚の生成 | `参考画像を生成` | まず1枚だけ生成し、確認を待つこと |
| 先行画像の了承と後続生成 | `了承して生成` | 了承後に比較用の偽画像を生成すること |
| 先行画像からの作り直し | `作り直す` | 参考画像1枚と後続画像の失効、残り回数 |
| 画像なしで進行 | `画像なしで進む` | 画像全体を比較に使わないこと |
| 全画像の確認と採用 | `最終確認へ` | 参考画像と偽画像の利用を了承して進むこと |
| 最終確認後の商品検索 | `検索` | この承認で商品検索を1回実行すること |
| 完了結果の表示 | `結果を見る` | 比較が完了した結果を開くこと |
| 安全に取消可能な検索の中止 | `検索を中止` | 取消可能な処理範囲 |
| 保存済み履歴の表示 | `開く` | 保存時点の結果を読み込むこと |
| 履歴削除の確定 | `削除` | 対象履歴と復元不能であること |
| 確認の取消 | `キャンセル` | 確定操作を実行せず戻ること |

##### ON/OFFのトグルスイッチ

`参考画像を使う` のようなON/OFFの切り替えは、幅56px・高さ32pxのトグルスイッチを共通部品として使う。背景はONが `#3a83f7`、OFFが `#424242`、移動する直径24pxの丸いつまみは常に `#ffffff` とし、ONは右、OFFは左へ配置する。既定値はOFFとする。

背景色とつまみの横移動は240msの `cubic-bezier(0.22, 1, 0.36, 1)` で滑らかに変化させる。切り替え途中で再操作した場合も現在の描画位置から最新のON/OFFへ移動し、`prefers-reduced-motion: reduce` では移動と背景色の変化を即時にする。トグルの両端と丸いつまみには `squircle` を適用しない。

ラベルに関連付けたネイティブcheckboxへ `role="switch"` を指定し、読み上げ名とON/OFF状態、Tab移動、Spaceでの切り替え、ラベルクリック、無効状態を維持する。処理中など変更できない状態では操作を受け付けない。

#### 13.6 全体の段階バー

「現在のページが全体のどの段階か」を画面中央上部のバーで示す。各段階の上に丸、下にテキストを配置する。バーの基本色は `#ffffff`、過去から現在まで通過した部分は `#3a83f7`。完了した段階の丸も背景を `#3a83f7` とし、未到達の丸は `#000000` とする。文字と指定のない外枠は `#ffffff` とする。

現在位置には、簡略化した人の上半身シルエットのアイコンを置く。外枠は `#ffffff`、背景は `#3a83f7`、シルエットは `#ffffff`。画面遷移に伴って現在位置を更新し、確認が無効になった後続部分は基本色へ戻す。アイコンを押して確認を飛ばす操作にはしない。

段階マーカーは現在の段階を44×44px、完了・未到達の段階を28×28pxとする。44×44pxの配置枠の中央へ置き、各丸の中心と接続バーを揃える。商品調査アイコンは36×36pxを保つ。白い丸枠はSVGの円と2pxのstrokeで描き、`vectorEffect="non-scaling-stroke"` と `shapeRendering="geometricPrecision"` を使う。枠を描画領域内に収め、拡大表示でも円周の欠けや線幅の不均一を抑える。

#### 13.7 画像生成と商品調査の動き

先行参考画像と比較画像の確認では、「条件へ戻る」「作り直す」を下部左側の同じ行へ32px間隔で並べる。画像なしで進む操作と了承・最終確認の主要操作は右側に配置する。

画像生成中の枠は背景を `#424242` とし、右上から左下へ光が波打つ効果を1.5秒間隔で繰り返す。その上に幅96px・高さ32px、文字14px・行高20pxの `生成中...` ポップを重ねる。末尾は空文字→`.`→`..`→`...`の4状態を0.5秒間隔で循環する。先行参考画像と比較用の偽画像の両方へ適用し、完了・失敗時は止める。再描画や連打でアニメーションや処理を重複起動しない。

商品調査ページは、全体の段階バーとは別の部品で5工程の状態を示す。

| 状態 | 工程行 | アイコン |
|---|---|---|
| 完了 | 基本背景に `完了` | 外枠・背景 `#ffffff`、チェックマーク `#000000`（24px・太さ700・行高24px、中央配置） |
| 現在 | 背景 `#424242`、`処理中...` | 外枠・背景 `#ffffff`、中央の丸 `#3a83f7` |
| 待機・失敗 | 基本背景に `待機` または `失敗` | 指定のない文字・外枠は `#ffffff`、装飾色を追加しない |

現在工程の丸は1.5秒周期で拡大・縮小を繰り返す。`処理中...` の末尾は画像生成と同じ4状態を0.5秒間隔で循環する。完了・失敗時は動きを止め、完了した工程を処理中へ戻さない。全工程完了後は全て完了アイコンとし、右側の `結果を見る` を有効にする。

### 14. オフラインモック

UIだけを確認できるよう、任意の自然言語入力から結果表示まで操作できるモックを [frontend/](../frontend/) に実装した。入力内容は確認画面に保持し、条件整理の応答・商品・画像には固定の合成データを用いる。入力から条件や商品を実際に推論・検索したとは表示しない。

検索画面を共通のReactコンポーネント・StyleX定義で実装し、現在のデータ供給と操作応答はmockだけとする。確認画面には元の入力と固定のデモ条件を区別して表示する。モック利用中であることは通常の文字・補足表示で明示し、専用の装飾色や設定画面を追加しない。

1. 自然文を入力し、`条件を整理` で固定の合成条件を表示する。
2. 条件確認から、画像ありなら参考画像1枚の生成中表示と確認へ進む。`了承して生成` の操作後だけ比較用画像の生成中表示と確認へ進む。
3. 画像なしなら画像生成を通らず最終確認へ進む。画像ありでは `最終確認へ` で全画像の利用を確認する。
4. 最終確認の `検索` 後に商品調査の5工程を模擬し、完了後の `結果を見る` で固定商品を表示する。
5. 戻る操作、内容変更に伴う後続確認の無効化、処理中の二重操作防止も再現する。

Noto Sans JPと画像はローカル資材として用意し、実バックエンド、Bonsai、外部API、認証情報を必要としない。実商品画像・CDN・外部フォントへ依存せず、モックから実サービスへ自動接続しない。モックの商品リンクは外部ページへ移動しない。アプリと資材をローカルから配信するための通信と、外部通信を区別する。

モックの成功は画面遷移・表示・操作だけの証拠であり、自然言語理解、実画像生成、商品取得、ランキング品質、実バックエンド接続の証拠にはしない。ブラウザ受入確認の結果と未接続範囲は [EXEC-117](GOAL.md#exec-117-react-stylexのオフライン画面) を正本とする。

#### 14.1 配置と実行手順

Node.js 22.12以上とnpmを使用する。最短の起動手順は [frontend/README.md](../frontend/README.md)、依存関係は [package.json](../frontend/package.json) と [package-lock.json](../frontend/package-lock.json) を参照する。React 19・TypeScript・Vite 8・StyleXを使い、[公式Vite統合](https://stylexjs.com/docs/learn/installation/vite/)に従って `@stylexjs/unplugin` がStyleXからCSSを生成する。共通トークン・画面部品・状態遷移・履歴の保存処理は [src/](../frontend/src/) に分離する。

環境準備はリポジトリ直下から行う。公開パッケージとChromiumの取得は通信を伴うが、アプリから実検索サービスへ接続する処理ではない。

```sh
cd frontend
npm ci
npx playwright install chromium
```

画面の起動:

```sh
npm run dev
```

`http://127.0.0.1:5173` をデスクトップブラウザで開く。Viteはloopbackだけで待ち受ける。Noto Sans JPは `@fontsource-variable/noto-sans-jp` の同梱資材、画像は [public/images/](../frontend/public/images/) の合成SVGをローカル配信する。

事前準備後の検証とビルド:

```sh
npm run check
npm test
npm run build
npm run test:e2e
UI_TEST_MODE=development npm run test:e2e -- controls.spec.ts
```

`npm run check` はTypeScriptとPrettier、`npm test` は状態遷移と履歴のVitest、`npm run test:e2e` はPlaywrightによるローカルブラウザ確認である。通常はビルド済み画面を4173番で起動し、`UI_TEST_MODE=development` では開発サーバーを5175番で起動して同じ操作部品を検証する。ブラウザ試験では合成入力だけを用い、外部通信を拒否する。ビルド済み画面だけを確認する場合は `npm run preview` で `http://127.0.0.1:4173` を開く。

GitHub Actionsの [frontendジョブ](../.github/workflows/ci.yml) はNode.js 22で型/整形・単体・build・ビルド版全画面テストと開発版の操作部品テストを実行する。Pythonジョブから独立し、各ブラウザ試験は1ワーカー・再試行なし・test.only禁止とする。追加後のGitHub上での実行結果は未確認であり、ローカル検証と区別する。

#### 14.2 モックのデータと保存範囲

- 任意の1〜2,000文字の入力を保持し、商品・必須・希望・除外・予算の5項目には固定のキーボード条件を表示する。編集内容を確認と履歴へ反映するが、商品12件・画像・順位は固定する。日本語/英語検索語の編集、明示価格と推定価格の分類、実条件抽出は未接続である。
- 参考画像は白いキーボード1枚、比較用の偽画像は色と形をそれぞれ変えた2枚とする。実際の画像生成や条件別の可変枚数生成は行わない。先行画像は検索計画ごとに最大2回、確認期限は15分、後続画像は1回の了承につき1回だけ表示を準備する。状態を戻しても作成回数は維持し、新しい検索で初期化する。
- 最終確認にも15分の期限を設け、期限切れでは再確認後に別の検索操作を必要とする。模擬処理中は二重開始を拒否し、破棄した処理の古い完了通知を受け付けない。実サービス用の承認・回数制御はserver側へ実装する契約を維持する。
- 0件を含む正常完了だけを、同じタブの `sessionStorage` へ最大30件・完了から30日間保存する。再読込では進行中の状態を初期化し、保存した履歴だけ再利用する。タブを閉じた後の復元や、別利用者の認証・server保存は提供しない。
- 保存・削除の失敗は表示し、再試行には利用者操作を必要とする。破損した履歴は固定メッセージで拒否し、入力や生例外をコンソールへ出さない。商品カードは合成商品であることを示し、実販売ページへのリンクは設けない。

#### 14.3 空結果と失敗表示の確認

起動URLのqueryで固定シナリオを選べる。通常の画面に設定画面を追加せず、queryは検証用の起動条件として扱う。例えば `http://127.0.0.1:5173/?scenario=reference-error` では参考画像の模擬処理を一度だけ失敗させる。再試行は通常の画面操作を使い、実サービスへ切り替えない。

| `scenario` | 確認する表示 |
|---|---|
| `empty` | 正常完了した0件結果と履歴 |
| `organize-error` | 条件整理の失敗と再試行 |
| `reference-error` | 先行画像の失敗と作り直し・画像なし続行 |
| `comparison-error` | 比較画像の失敗、部分採用の拒否、先行画像からの作り直し |
| `research-error` | 商品調査の失敗と最終確認からの再試行 |
| `save-error` | 履歴保存の失敗と再試行、未保存結果を離れる確認 |
| `delete-error` | 履歴削除の失敗と再試行 |

失敗シナリオはページの再読込で初期化する。模擬失敗の回復確認を実APIの障害回復や料金制御の検証とは扱わない。
